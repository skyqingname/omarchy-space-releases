# Windows：从“拒绝访问”到文件附件验收

记录日期：2026-11-12。原安装包为 GoToCS 0.1.0 Windows x64；本次源码基于 `512d0db68b86bf957d21688dac0f47c4daffd7e7`。以下区分本机环境修复、当前源码已有能力、本 PR 新增修复和仍待处理的问题。环境能启动、构建成功与端到端验收是不同结论。

## 故障与处理

| 阶段 / 现象 | 定位与处理 | 本 PR 中的状态 |
| --- | --- | --- |
| 数据目录“拒绝访问” | Windows 当前账户对选定的数据目录缺少写入权限。为该账户授予该目录及子项的“修改”权限后继续运行。 | 记录本机 ACL 修复；不在程序里自动扩大权限，不删除或重建虚拟磁盘。 |
| 缺少启动资源 | Windows 客机启动除磁盘镜像外还需要匹配的 `vmlinuz-linux` 和 `initramfs-linux.img`。补齐匹配资源后继续启动。 | 当前 `runtime-profiles.json` 已列出三项镜像资源；不提交二进制资源或个人镜像。 |
| 图形初始化失败 | 当前硬件图形路径不兼容；关机后启用已有“兼容显示”，使用 CPU 渲染后能够进入客机。 | 当前源码已有此选项及持久化支持；不增加自动模式重试。 |
| 首次账号设置未完成 | provisioning 等待用户完成客机账号设置；用户完成后继续初始化及重启核验。 | 正常的用户步骤，不能通过伪造 ready 跳过。 |
| 客机配置受缺少 `ufw` 阻塞 | 当前客机镜像缺少配置终端时调用的 `ufw`。在停机状态下，以签名软件包和可回退的离线副本补装，验证后写回原盘。 | 记录已完成的本机修复。源码仍直接调用 `ufw`，镜像依赖自检/自动补齐尚未实现；本 PR 不宣称修复所有新镜像的这一问题。 |
| 节点连接与初始化网络失败 | 分别检查所选节点的 DNS、TCP、代理出口与下载链路，处理该节点的引导解析问题，再验证 TUN/代理出口与断网保护。 | 节点参数属于用户配置；不硬编码个人节点、引导 IP 或凭据，不放开直连回退。 |
| Claude 安装与 API 配置 | 处理客机安装链路，使用 Claude 官方安装器，并在客机设置 API 地址及凭据后完成真实请求。 | 当前源码已有官方安装器。个人 API 地址、Key 和账号设置均不进入 PR。 |
| API 已能请求，图形框仍提示“先登录” | 旧跟随脚本仅以 OAuth 凭据文件判断登录。新增环境变量、用户设置和启动设置中非空 `ANTHROPIC_AUTH_TOKEN` / `ANTHROPIC_API_KEY` 的识别。 | 新增源码修复及 10 项回归；保留首次引导、目录信任判断。仅配置地址不算凭据，实际凭据有效性仍由 API 服务验证。 |
| Windows 文件无法交给客机 Claude | 外层对话缺少附件入口；粘贴 Windows 路径或复制文件不会自动传输字节，浏览器文件选择器只看到客机目录。 | 新增附件按钮、GoToCS 对话页拖放处理、队列/进度/取消/重试和 SSH 客机接收协议，详见 [attachments.md](attachments.md)。 |
| 重建版启动报 OS error 206 | 内联 provisioning OEM 字符串导致 Windows 创建进程的命令行过长。Windows 改为写文件，再通过 QEMU `-smbios type=11,path=...` 读取同一内容。 | 新增源码修复及长度/内容回归；真实客机重启并返回 ready。其他平台保留原方式。 |
| Windows 存储单测失败 | 预期路径未处理 `\\?\` 前缀，而业务逻辑已做路径规范化。 | 仅修正两处测试的预期路径，不改变存储选择逻辑。 |

初期对安装 EXE 中嵌入的登录状态脚本做过本地修复；本 PR 将相应逻辑放回 Python 源码。不分发修改后的 EXE，也不提供针对其他版本的二进制替换补丁。

## Windows 实际使用结果

- **外层对话**：中文消息、工具执行、创建/读取客机文件、历史会话切换恢复均可用；真实往返结果已检查。
- **内置终端**：中文输入、执行过程和对话同步可用。当前 Claude 终端中文字粘贴使用 `Ctrl+Shift+V`；`Ctrl+V` 会走 Claude 图片粘贴路径，并可能提示 SSH 下无图片。
- **内置浏览器**：用户解锁后可访问网页、滚动、粘贴网址，并通过网页文件选择器上传客机 TXT。自建接收页返回 HTTP 200，收到的字节与原客机文件一致。临时测试服务已停止。
- **完整虚拟机桌面**：解锁后可以浏览文件；窗口放大改善可读性。部分菜单为日文，中文文档显示正常。
- **新增附件按钮**：Windows 原生程序多选 DOCX、PDF、中文 TXT、空文件和 1 MiB 二进制文件，均经真实 SSH 传入客机；五个文件的大小和 SHA-256 由独立脚本及宿主只读磁盘检查核对一致。
- **实际读取**：Claude 通过客机工具读取 DOCX、PDF、TXT 正文和测试标记。DOCX 使用 Python ZIP/XML，PDF 使用已有 `pdftotext`。未据此宣称支持所有格式解析或 OCR。
- **失败恢复**：512 MiB + 1 字节文件被拒绝；缩小同一测试文件后点击重试成功。取消 128 MiB 上传后，客机未发现完成文件或 `.partial` 遗留。

## 尚未解决或尚未验收

1. **睡眠/锁屏时浏览器灰屏**：曾观察到物理输出及无头浏览器输出 DPMS 关闭；按当前镜像的 Hyprland Lua 接口唤醒、用户手动解锁后恢复。未修改持久休眠或锁屏设置；软件尚无清晰状态提示/恢复引导，不能断言所有灰屏同因。
2. **Apps 菜单**：当前镜像缺少 `walker` 和 `elephant`，点击菜单未显示应用列表，尚未补齐。
3. **TXT 默认打开**：文件管理器能显示文件，但未看到编辑器打开；`nvim`、`foot` 存在，具体启动失败原因仍待排查。
4. **显示布局和语言**：窗口可能落到无头浏览器输出；本次仅临时移动测试窗口。小窗口可读性、部分界面语言体验仍需改善，未改变按节点出口配置地区的策略。
5. **物理拖放**：原生拖放事件处理通过组件测试；Windows 资源管理器跨窗口真实拖拽未完成有效验收。外部 QEMU 桌面窗口没有新增拖放能力。
6. **平台及故障注入**：新增功能的 macOS 实机、真实 SSH 中断、传输超时及上传中关机未完成设备验收。主机或客机强制掉电可能留下 `.partial`；应用不会将其标记为成功附件。
